# Development Guide

This is a practical guide to working on this codebase day to day. For the one-time setup and the
`docker compose up` path, see the **Quick Start** section in the root [README.md](../README.md) —
this document assumes you've done that once and covers what the Quick Start doesn't: what the
tooling config actually does, how migrations and seeding work under the hood, and how to run tests
and linting for both halves of the stack.

## Backend tooling: what `pyproject.toml` actually enforces

`backend/pyproject.toml` defines the package (`stone-crusher-backend`, Python 3.12+) and three
dependency groups:

- **Base `dependencies`** — what the app needs to run at all: FastAPI, async SQLAlchemy, `asyncpg`,
  Alembic, Pydantic v2/pydantic-settings, `argon2-cffi` (password hashing), `pyjwt`, `httpx`.
- **`[project.optional-dependencies] azure`** — `azure-storage-blob`, `azure-identity`,
  `opencensus-ext-azure`. Kept out of the base install deliberately: local development and the test
  suite always use `STORAGE_PROVIDER=local` and stdout logging, so pulling in the Azure SDK's large
  dependency tree on every local `pip install` would slow down the one path almost every
  contributor actually runs. Install with `pip install -e ".[azure]"` before deploying, or rely on
  the Docker image, which installs it explicitly.
- **`[project.optional-dependencies] dev`** — `pytest`, `pytest-asyncio`, `pytest-cov`, `aiosqlite`
  (the async SQLite driver the test suite runs on), `ruff`, `black`, `mypy`, `pip-audit`,
  `factory-boy`. This is what `pip install -e ".[dev]"` in the Quick Start actually pulls in.

Three tool sections configure the quality gates that also run in CI (`azure-pipelines.yml`'s Lint
and Test stages):

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"     # every `async def test_...` runs as a coroutine without @pytest.mark.asyncio
testpaths = ["tests"]

[tool.ruff]
line-length = 100
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]   # pycodestyle, pyflakes, isort, bugbear, pyupgrade
ignore = ["B008"]                     # B008: "function call in default argument" — FastAPI's
                                       # `Depends(...)` pattern requires this and would otherwise
                                       # be flagged on every route in the codebase

[tool.black]
line-length = 100
target-version = ["py312"]

[tool.mypy]
python_version = "3.12"
ignore_missing_imports = true      # don't fail on untyped third-party stubs
disallow_untyped_defs = false      # not a fully-typed-everywhere codebase yet; opt in per-module
```

The `B008` ignore is the one worth remembering if you add a new linter rule locally and wonder why
it doesn't fire: it's not an oversight, it's there because `Depends(get_db)`-style defaults are the
FastAPI idiom used throughout `app/api/v1/`.

Run all three locally exactly as CI does:

```bash
cd backend
ruff check app tests
black --check app tests
mypy app
```

`black --check` only reports; run `black app tests` (no `--check`) to actually reformat.

## Database migrations

Alembic is configured in `backend/alembic/env.py`. Two details matter if you're used to a
boilerplate Alembic setup:

- `env.py` imports `app.models` (not individual model modules) before reading `Base.metadata`, so
  every model in the codebase is guaranteed to be registered before `alembic revision --autogenerate`
  runs. If you add a new model file and forget to import it from `app/models/__init__.py`, autogenerate
  will silently not see it — always add new models there.
- It reads `settings.database_url` directly (`config.set_main_option("sqlalchemy.url", ...)`)
  rather than a hardcoded URL in `alembic.ini`, so migrations run against whatever `DATABASE_URL`
  your environment resolves to — the same `.env` the app itself reads.

Common commands, from `backend/`:

```bash
alembic upgrade head                              # apply all pending migrations
alembic revision --autogenerate -m "add widgets"  # generate a new migration from model changes
alembic downgrade -1                              # roll back the most recent migration
```

As of this writing there is exactly one migration
(`faf06f89c6a6_phase_0_platform_foundation.py`, `down_revision = None`) — the entire Phase 0 schema.
Always review an autogenerated migration before committing it; Alembic's diffing is good but not
infallible, particularly around enum types and server defaults.

## Seeding local data

`backend/app/core/seed.py` is an idempotent script — every insert checks for an existing row by its
natural key first, so it's safe to run repeatedly against the same database (rerunning it after
pulling new code that adds a permission, for instance, will just add the new permission without
duplicating anything else). Run it with:

```bash
python -m app.core.seed
```

It seeds, in order:

1. **The fixed permission set** — the `PERMISSIONS` list in the script (`users.view`,
   `roles.create`, `tenants.delete`, `audit.view`, ...), each tagged with a module.
2. **The seven system roles** — `SUPER_ADMIN`, `TENANT_ADMIN`, `MANAGER`, `OPERATOR`,
   `ACCOUNTANT`, `STOREKEEPER`, `VIEWER` — each pre-wired with a sensible permission subset (e.g.
   `VIEWER` only gets `dashboard.view` and `documents.view`; `TENANT_ADMIN` gets everything except
   platform/tenant-management permissions, which are reserved for `SUPER_ADMIN`).
3. **A platform super admin user** — `is_platform_user=True`, `tenant_id=None`, assigned the
   `SUPER_ADMIN` role. Email and password come from the `SEED_SUPER_ADMIN_EMAIL` /
   `SEED_SUPER_ADMIN_PASSWORD` environment variables, defaulting to a clearly-fake local-only
   credential (`superadmin@stonecrusher.example.com` / `ChangeMe!12345`) if unset — set both in any
   environment that isn't a throwaway local database.
4. **A demo tenant** (`DEMO` / `demo`, "Demo Stone Crushers") **with one user per non-platform
   role** — `admin@demo.stonecrusher.example.com` through `viewer@...`, all sharing the password
   `Demo!12345`, all tenant-wide scoped (no `organization_unit_id`) so you can log in as each role
   and see the permission differences immediately without first having to set up plants/sites.
5. **A base unit-of-measure set** — `UnitCategory`/`Unit`/`UnitConversion` rows for mass, volume,
   distance, time, and count (kg, ton, litre, km, hour, piece, set), including the kg<->ton
   conversion factor — the minimum reference data business modules will need later.

## Frontend dev workflow

`frontend/` is Angular 22 with Angular Material 3 and strict TypeScript. The `package.json`
scripts:

```bash
npm start   # ng serve — dev server on http://localhost:4200 with live reload
npm run build   # ng build — production build to dist/
npm test    # ng test — unit tests
npm run lint   # ng lint — ESLint via angular-eslint
```

Two things worth knowing that aren't obvious from the script names:

- **Unit tests run on Vitest, not Karma.** `angular.json`'s `test` target uses the
  `@angular/build:unit-test` builder (Angular 22's newer, faster test runner), with
  `src/test-setup.ts` as the setup file — there is no `karma.conf.js` and no Chrome/ChromeHeadless
  dependency for local runs. (CI's `azure-pipelines.yml` still passes `--browsers=ChromeHeadless`
  to `npm test`, which is a holdover — check what version of the pipeline you're actually running
  against if that flag matters to you.)
- **`.env` is not read by the Angular build.** `frontend/.env.example` is explicit about this:
  Angular's build-time configuration lives in `src/environments/environment.ts` /
  `environment.prod.ts`, and `.env` only supplies process environment variables to the dev
  container (e.g. `NG_CLI_ANALYTICS=false`). If you need to change the API base URL the frontend
  talks to, edit the environment file, not `.env`.

The frontend's module layout under `src/app/` mirrors the backend's Phase 0 surface directly:
`auth`, `users`, `roles`, `tenants`, `settings`, `audit`, `dashboard`, plus a `core/` module holding
cross-cutting concerns (the auth service, HTTP interceptors for the bearer token and error envelope,
route guards) and `shared/` for reusable UI. There is no frontend module yet for anything not
already listed as a Phase 0 backend router.

## Running tests

**Backend:**

```bash
cd backend
pytest -v                    # full suite
pytest -v tests/test_auth.py # a single file
pytest --cov=app             # with coverage, as CI runs it
```

**Frontend:**

```bash
cd frontend
npm test                     # watches by default in dev; CI passes --watch=false
npm run build                # also worth running locally — catches strict-mode TS errors tests won't
```

### Why the backend test suite runs on SQLite, and what that cost

`backend/tests/conftest.py` builds every test database as an **in-memory SQLite** engine (via
`StaticPool`, so all connections within one test see the same schema and data), not PostgreSQL.
This is a deliberate speed trade-off — the full suite runs in seconds, anywhere, with no database
server to start — and it's explicitly documented as safe *because* every model column uses
SQLAlchemy 2.0's dialect-agnostic types (`Uuid`, `JSON` via `portable_json()`) rather than
Postgres-specific ones directly (see `app/models/base.py`). The exact same model definitions run
against PostgreSQL in production and SQLite in tests — there is no separate "test schema."

That portability isn't free, though, and this codebase has hit both of the sharp edges that come
with running the same code on two different SQL engines:

- **Naive vs. aware datetime comparisons.** PostgreSQL's `TIMESTAMPTZ` preserves timezone info on
  round-trip; SQLite has no timezone-aware storage type, so a plain `DateTime(timezone=True)`
  column silently comes back as a **naive** datetime when read from SQLite. Any code that then
  compares it against `datetime.now(timezone.utc)` (an aware datetime) raises `TypeError: can't
  compare offset-naive and offset-aware datetimes` — a bug that only reproduces against SQLite,
  meaning it can pass locally against Postgres and fail in the test suite, or vice versa, depending
  on which one you're comparing against. The fix was the `UTCDateTime` type decorator in
  `app/models/base.py`, which every timestamp column in the codebase uses instead of
  `DateTime(timezone=True)` directly — it re-attaches UTC tzinfo on read if the driver returned a
  naive value, so `created_at`/`updated_at`/etc. behave identically regardless of which database
  produced them.
- **`MissingGreenlet` from a column that wasn't eagerly refreshed.** `TimestampMixin.updated_at`
  has `onupdate=func.now()`, a server-computed value. By default, SQLAlchemy leaves such a column
  *expired* on the ORM object after a flush, to be refetched lazily the next time it's accessed —
  fine under sync SQLAlchemy, but under `asyncio` that implicit lazy-load happens outside the
  session's IO-bridging greenlet context and raises `MissingGreenlet` the moment something (like
  serializing the object into a response schema right after a commit) touches the attribute. The
  fix was setting `eager_defaults = True` on `Base.__mapper_args__` (`app/core/database.py`), which
  makes SQLAlchemy fetch server-computed columns via `RETURNING` as part of the flush itself, so
  they're already populated by the time anything reads them.

Both were real bugs caught by running the same models against both dialects, not theoretical
concerns — which is the actual argument for keeping the test suite on SQLite rather than switching
it to Postgres-only: it forces exactly this class of bug to surface early, in a fast local run,
instead of only in a staging environment that happens to be running Postgres.

### On not having Docker/Postgres everywhere

Not every environment this code gets worked on in has Docker Desktop or a local PostgreSQL install
available. That's fine for the backend: `pip install -e ".[dev]"` plus `aiosqlite` is enough to run
the entire test suite and even `uvicorn app.main:app --reload` against a local SQLite file (point
`DATABASE_URL` at `sqlite+aiosqlite:///./dev.db` and run `alembic upgrade head`) for basic
API-shape work. What you lose without a real Postgres instance:

- Anything that depends on `JSONB`-specific behavior (`portable_json()` degrades to plain `JSON` on
  SQLite — functionally fine for typical read/write, but not a place to validate Postgres-specific
  query behavior).
- Realistic connection-pool behavior (`pool_size`/`max_overflow` are Postgres-only settings; SQLite
  gets no pooling tuning at all).
- Parity with what actually runs in CI's `BackendTests` job and in production, both of which are
  Postgres.

Treat SQLite-backed local runs as fine for fast iteration on business logic, but always run the
full stack against `docker compose up` (real Postgres) before considering a change involving schema
or connection behavior done.
